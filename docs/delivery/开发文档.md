## 二、总体架构

### 2.1 架构形态

后端采用 Spring Boot 3.3、Java 17 的模块化单体。模块在同一 API 进程内运行，通过 AgriStore 统一访问持久化记录，通过 AgriEventBus 发布实时事件。当前不拆分微服务，不在发布环境重新编译源码。

~~~text
Web/Vue + ECharts       微信小程序       BearPi 串口桥
        │                    │                │
        └────── HTTPS/REST/SSE ───────┐       │ MQTT
                                      ▼       ▼
                                AgriController
                                      │
                                  AgriEngine
       ┌──────────────┬───────────────┼───────────────┬─────────────┐
       ▼              ▼               ▼               ▼             ▼
  CropPackCatalog  规则/诊断       处方/安全门    Agent 工具     SimulationEngine
       │              │               │               │             │
       └──────────────┴─────── AgriStore / EventBus ──┴─────────────┘
                                      │
                         PostgreSQL / Redis Streams / MQTT
~~~

### 2.2 不变量

1. 浏览器不直接连接 MQTT，不暴露 Redis、数据库或模型凭据。
2. 模拟器运行在 API 进程内的 SimulationEngine；模拟事件只能经 AgriEngine.ingest 进入统一校验、落库和事件发布流程。
3. Agent 只能调用注册表中的工具，不能拼接 SQL、MQTT topic、任意 HTTP 或 Shell 命令。
4. 权限、数据新鲜度、质量、设备健康、资源和幂等校验在领域服务执行时再次检查，不能只相信 JWT 或模型输出。
5. 模拟数据标记 sourceMode=SIMULATION；真实 BearPi 数据必须标记 sourceMode=REAL、provenance=OBSERVED、dataOrigin=HARDWARE。

## 三、三条数据主线

### 3.1 数据主线

输入可以来自 SimulationEngine、BearPi 桥接器或受保护的 REST 遥测接口。AgriEngine 对 eventId、地块、设备、指标、时间戳、质量和来源进行规范化，AgriStore 写入 telemetry，并记录 event_log。重复 eventId 返回 duplicate，不重复写入。Redis 可用时同时写入 agri.telemetry Stream，由 RedisStreamWorker 消费；失败记录进入 DLQ 并保留审计。

### 3.2 智能体主线

Agent 对话先读取当前账号、角色、农场/地块范围和最新事实，再识别查询、诊断、导航或操作意图。只读工具直接返回事实；有副作用的工具先产生 actionProposal，用户确认后由 AgriEngine 重新执行权限、安全门、资源和幂等检查。模型不可用时返回规则/检索结果并标记降级，不改变领域结果。

### 3.3 可视化主线

Web 和微信端只调用 REST 和 SSE。前端使用 role、farmIds、plotIds 过滤页面数据，实时事件按事件类型更新告警、任务、设备和曲线。页面不保存数据库凭据，也不把 SSE 事件当成最终事实；刷新时重新从 REST 读取。

## 五、Web、微信小程序与硬件端

### 5.1 Web UI

apps/web-ui 使用原生 Vue 全局运行时、ECharts 和必要的 Three.js 兼容资源，由 Vite 7.1.5 构建五个入口：index.html、sysadmin.html、farmer.html、login.html 和 login-concepts.html。Vite base 为相对路径，Nginx 通过四个前缀路由到静态文件。当前运行页面使用内联场景图形和登录页 WebGL；旧背景、ORT、ONNX 和场景脚本不进入发布包。

前端 API 会话、角色和来源标签集中在 apps/web-ui/js/api.js、roles.js、live-data.js 等模块；页面不直接读取服务端文件系统。

### 5.2 微信小程序

apps/wechat-mini-program 使用 utils/api.js 和 utils/session.js 访问同一 REST 合同，页面包括登录、首页、地块、任务和个人资料。发布 ZIP 不包含微信小程序源码；源码压缩包保留它用于后续开发。小程序验收脚本为 scripts/check-wechat-mini-program.mjs。

### 5.3 硬件端

支持的真实硬件链路为 BearPi HM Nano + E53_IA1。hardware/bearpi_e53_bridge.py 和 docs/hardware/bearpi-e53-ia1.md 描述串口、MQTT 和 ACK 合同。仅设备 bearpi-e53-ia1-a01 接受风扇 FAN_SET 和补光灯 LIGHT_SET；固定 AT+AGRI 指令经固件切换 GPIO 并返回 AGRI_ACK 后才写入成功状态。真实水泵、阀门、其他传感器、其他 GPIO 执行器、鸿蒙端和生产级视觉/语音需要另行适配。

## 六、认证、JWT 和三角色权限

### 6.1 登录流程

POST /api/v1/auth/login 接收 username、password 和可选 role，服务端使用 BCrypt 校验 user_account.password_hash，成功后签发 JWT。JWT 包含 userId、username、role、farmIds、plotIds 和 credentialVersion；密码、恢复码和哈希不会返回。每个受保护请求会重新读取账号范围，账号停用或 credentialVersion 变化可立即使旧令牌失效。

### 6.2 角色矩阵

| 角色 | 数据范围 | 主要写入能力 |
|---|---|---|
| FARMER | 自己授权的地块和关联农务 | 巡田、补证、本人任务、通过安全门的虚拟灌溉 |
| FARM_ADMIN | 授权农场的全部地块 | 地块/设备/成员/工单/告警治理和虚拟控制 |
| SYSTEM_ADMIN | 平台治理和跨农场只读范围 | 平台账号、规则/Crop Pack、案例审核和策略状态；不直接替代农场生产事实 |

范围判断同时检查 farmIds、plotIds、角色和对象之间的 farmId/plotId 一致性。SYSTEM_ADMIN 的平台能力不是绕过审计的超级用户。

### 6.3 密码和账号

演示种子中的 farmer、admin、sysadmin 初始密码均为 demo123，仅用于验收。正式环境通过改密或账号管理接口设置新密码；恢复码只在成功响应中展示一次，服务端只保存 BCrypt 哈希。JWT_SECRET、数据库密码和 SYSTEM_ADMIN_AUTHORIZATION_CODE 只通过受保护环境文件传入。

## 七、数据库表与 Flyway 迁移

### 7.1 物理表

| 表 | 用途 |
|---|---|
| entity_record | 以 entity_type + entity_id 为主键保存农场、地块、设备、作物批次、计划、告警、工单、诊断、Agent 会话等 JSON 记录 |
| telemetry | 结构化遥测事件、质量、场景、分支和来源字段 |
| event_log | 业务事件、trace、场景和审计 payload |
| idempotency_key | 控制命令和其他写操作的一次性键 |
| user_account | 账号、角色、农场/地块范围、凭据版本和启用状态 |
| external_identity | 可选社会身份映射，外键指向 user_account |

### 7.2 迁移

运行时由 Flyway 执行：

~~~text
V1__agriloop_core.sql
V2__account_management.sql
V3__social_identity.sql
V4__three_role_scopes.sql
V5__telemetry_source_provenance.sql
~~~

V1 创建核心表和索引；V2 增加账号恢复码、凭据版本和时间字段；V3 增加外部身份；V4 兼容旧角色并规范三角色范围；V5 增加 source_mode、provenance、data_origin 及来源索引。迁移脚本使用 IF NOT EXISTS 或可重复 ALTER，不能手工修改 flyway_schema_history。

### 7.3 演示种子

database/demo-seed.sql 和交付目录中的副本只写入 farm-demo、plot-a01、plot-a02、plot-b01、mock-*、batch-*、resource-default、case-seed-001 至 case-seed-003 及三账号。脚本采用固定 ID、固定 BCrypt 哈希和 ON CONFLICT DO NOTHING；不删除、覆盖其他业务记录，也不包含遥测历史。发布环境 SEED_DATA=false，由安装脚本在 API 健康后按 DEMO_SEED 决定是否执行。

## 八、REST、MQTT、Redis Streams 与 SSE 合同

### 8.1 REST 通用约定

所有 REST 路径以 /api/v1 开头，除登录、注册、密码重置和健康检查外需要 Authorization: Bearer <JWT>。成功响应结构：

~~~json
{
  "requestId": "uuid",
  "timestamp": "2026-01-01T00:00:00Z",
  "schemaVersion": "1.0",
  "data": {}
}
~~~

错误响应的 error 对象包含稳定 code、message 和 details。完整 128 个路径、参数和 JSON Schema 以 docs/api/openapi.yaml 为准。常用分组如下：

| 分组 | 典型路径 |
|---|---|
| 认证 | /auth/login、/auth/me、/auth/change-password |
| 总览与农场 | /overview、/farms、/plots、/plots/{plotId}/health |
| 遥测与实时 | /plots/{plotId}/telemetry、/telemetry、/events/stream |
| 诊断与预测 | /diagnoses/evaluate、/rules/evaluate、/plots/{plotId}/risk-forecast、/forecasts/evaluate |
| 处方与执行 | /irrigation/estimate、/commands/virtual、/commands/{commandId}/ack、/lighting/virtual |
| 农务治理 | /work-items/today、/work-orders、/alerts、/inspections |
| Agent | /agent/chat、/agent/actions/{actionId}/confirm、/agent/tools、/decision-passports/{traceId} |
| 情景与资源 | /scenarios/runs、/scenarios/compare、/resource-plans/evaluate、/value-ledgers |
| 管理 | /farm-members、/users、/devices、/crop-packs、/strategy-candidates |

关键请求必须带稳定的 plotId、farmId 和 idempotencyKey；服务端不接受模型拼接的 URL 或 topic。

### 8.2 遥测事件

TelemetryEvent 至少包含 eventId、plotId、deviceId、metric、value 和 ts；推荐同时提供 farmId、unit、quality、scenarioId、branchId、sourceMode、provenance 和 dataOrigin。指标编码包括 SOIL_MOISTURE、AIR_TEMPERATURE、AIR_HUMIDITY、LIGHT、CO2、PH、WATER_LEVEL 和 RAINFALL。sourceMode=SIMULATION 的事件只能表示模拟观察；REAL/HARDWARE 输入必须保留真实来源。

### 8.3 MQTT

Broker 默认只绑定 tcp://127.0.0.1:1883，QoS 为 1：

~~~text
agri/{farmId}/{plotId}/telemetry       设备/模拟器 -> API
agri/{farmId}/{plotId}/device/status   设备状态 -> API
agri/{farmId}/{plotId}/command         API -> 执行器/硬件桥
agri/{farmId}/{plotId}/command/ack     执行器/硬件桥 -> API
~~~

命令 topic 和参数由后端根据已授权对象生成。BearPi ACK 需要 commandId、deviceId、actuator、targetState、actualState、status、result、executionMode、sourceMode、dataOrigin 和 provenance。串口失败、固件拒绝或 ACK 超时必须成为 FAILED/TIMEOUT，不能把目标状态当成实际状态。

### 8.4 Redis Streams

RedisStreamWorker 使用 stream agri.telemetry、消费组 agriloop-api、消费者 api-worker。有效消息进入 AgriEngine.ingest 并确认；缺少 payload 或处理失败的消息进入 agri.telemetry.dlq，同时写入 dead-letter 审计。Redis 不可用时 API 保留明确降级状态，数据库和规则路径仍可工作，但不应声称实时 Streams 已可靠处理。

### 8.5 SSE

GET /api/v1/events/stream 返回 text/event-stream。AgriEventBus 保存带 UserPrincipal 的连接，按账号农场/地块范围过滤事件，发送心跳并在断开、超时或异常时移除连接。前端只把 SSE 用作刷新提示和实时增量，最终状态必须回查 REST。

## 九、遥测、诊断、处方、审批和虚拟执行流程

### 9.1 遥测到告警

~~~text
采样/设备输入
  -> 事件字段和来源校验
  -> 去重、质量/新鲜度计算
  -> telemetry 落库
  -> 设备状态和规则计算
  -> 告警、诊断候选、event_log、Redis Stream、SSE
~~~

模拟器不能直接写告警。数据质量 BAD、STALE、DRIFT、冲突或设备离线时，诊断会列出支持、反对和缺失证据，并把就绪度降为 NEEDS_EVIDENCE、HUMAN_REVIEW 或 UNAVAILABLE。

### 9.2 灌溉建议和安全门

POST /api/v1/irrigation/estimate 使用同一份最新快照解析系统默认、Crop Pack、阶段、农场和地块参数，生成 irrigation-plan、diagnosis、readiness 和 hardGates。可执行处方必须同时满足指标存在、GOOD 质量、新鲜度、设备健康、账号权限、水资源/每日上限、冷却和时长上限。安全策略否决优先于模型建议。

### 9.3 确认、命令和效果

~~~text
处方 PROPOSED
  -> 当前操作人 confirmed=true
  -> 权限/安全门/幂等键重新检查
  -> command CONFIRMED/APPROVED
  -> MQTT 或内存回退传输
  -> ACK SUCCEEDED/PARTIAL/FAILED/TIMEOUT
  -> evaluation COMPLETED/PARTIAL/INCONCLUSIVE/PENDING
  -> 土壤湿度、水位和 water-daily-balance 效果记录
~~~

虚拟执行不会等待真实时长；异步 ACK 在约束窗口内到达后才更新终态。重复 idempotencyKey 返回第一次 command，不产生第二次动作。没有足够基线、ACK 或失败结果时，评价不能标记为成功。

### 9.4 光照

光照计划和灌溉复用诊断、就绪度、确认、幂等和效果合同。Crop Pack 的日间目标和 Asia/Shanghai 时段决定 LIGHT_BOOST 是否需要；夜间或目标范围内返回 NO_ACTION，不生成可执行命令。当前只支持虚拟补光，真实板载补光灯另受 BearPi 合同约束。

### 9.5 情景和最小双轨

POST /api/v1/scenarios/runs 使用固定 scenarioId 和 seed 生成可回放事件；POST /api/v1/scenarios/compare 使用同一冻结快照和随机种子生成 EXECUTE/NO_ACTION 双轨。分支是只读试算，不回写主遥测、命令或资源状态。演示脚本应固定 seed=42 以便复现。

## 十、Agent 工具调用与降级策略

### 10.1 工具边界

GET /api/v1/agent/tools/catalog（兼容 /agent/tools）返回工具名称、角色、targetScope、riskLevel、requiresConfirmation 和 inputSchema。只读工具可查询地块、遥测、诊断、预测、作物手册、告警、任务、资源、设备和治理状态；写工具包括创建地块/成员、工单、巡田、补证、虚拟灌溉、账号和策略治理。

工具参数先由 AgentToolRegistry 校验，再由领域服务校验。工具不能接收 SQL、任意 URL、任意 MQTT topic 或 Shell 字符串。

### 10.2 预览和确认

有副作用的 Agent 请求保存 agent-run、agent-action 和 conversation/message，返回 actionProposal，状态通常为 AWAITING_CONFIRMATION。只有同账号、同 conversationId、唯一且未过期的预览，才接受 /agent/actions/{actionId}/confirm。确认时重算权限、地块/农场一致性、安全门、资源、设备和幂等；取消或冲突会保留审计原因。

虚拟灌溉 action 的状态序列为 AWAITING_CONFIRMATION -> EXECUTING -> SUCCEEDED/PARTIAL/FAILED/TIMEOUT。前端轮询后端终态，等待中的 EXECUTING 不得显示为失败。

### 10.3 学习和策略候选

ControlledLearningService 只使用有完整快照、诊断、ACK、效果和质量证据的案例。质量状态为 PENDING、QUALIFIED 或 REJECTED；合格案例才可用于正向检索或候选策略。候选必须经过 DRAFT -> OFFLINE_VALIDATED -> APPROVED -> ACTIVE，失败或撤回进入 REJECTED/ROLLED_BACK。生产不会静默修改阈值、规则或模型权重。

### 10.4 模型降级

推荐的本地模型配置为 Qwen3.8-27B + vLLM。使用该配置时，GPU 总显存建议不低于 90 GB，并应根据模型权重和上下文长度预留磁盘及系统内存：

~~~dotenv
AI_MODE=openai-compatible
LLM_BASE_URL=http://127.0.0.1:8000/v1
LLM_MODEL=Qwen3.8-27B
~~~

模型标识为 `Qwen/Qwen3.8-27B`。下载地址和下载工具如下，开发、部署或测试环境选择一个入口即可：

| 来源 | 地址 |
|---|---|
| Hugging Face 官方 | <https://huggingface.co/Qwen/Qwen3.8-27B> |
| Hugging Face 国内镜像 | <https://hf-mirror.com/Qwen/Qwen3.8-27B> |
| ModelScope 国内镜像 | <https://modelscope.cn/models/Qwen/Qwen3.8-27B> |

~~~bash
# Hugging Face 官方
python3 -m pip install --upgrade "huggingface_hub[cli]"
hf download Qwen/Qwen3.8-27B --local-dir /srv/models/Qwen3.8-27B

# Hugging Face 国内镜像（二选一）
export HF_ENDPOINT=https://hf-mirror.com
hf download Qwen/Qwen3.8-27B --local-dir /srv/models/Qwen3.8-27B

# ModelScope 国内镜像（与 Hugging Face 二选一）
~~~

模型未启动、超时或返回结构不合规时切换：


响应和页面明确显示规则模式或 degraded 原因。模型不可用不影响确定性安全门，不能将规则结果写成模型推理。

## 十三、测试策略与验收脚本

### 13.1 单元和集成

后端 JUnit 覆盖认证、角色范围、Crop Pack、质量/新鲜度、安全门、诊断、处方、幂等、命令 ACK、效果评价、情景回放和资源约束。AgriStore 使用 H2 测试 profile；PostgreSQL 迁移在发布安装检查中执行。Redis/MQTT 集成需要对应服务可用，服务不可用时检查降级字段。

### 13.2 前端回归

apps/web-ui/test 下的 Node 测试覆盖会话、农户 P0、管理页面、告警、工单、作物、资源、预测和导航。有效的视觉辅助脚本为：

~~~text
scripts/visual-check.mjs
scripts/crop-shot.mjs
scripts/height-check.mjs
~~~

浏览器回归需覆盖桌面和窄屏入口、登录、角色切换、实时数据、灌溉预览/确认、消息和规则降级状态。

### 13.3 黑盒验收

scripts/acceptance_smoke.py 只使用公开 REST 合同，验证登录、总览、遥测去重、诊断、处方、预测、资源超限、命令幂等、失败效果和情景运行。执行前设置：

~~~bash
BASE_URL=http://127.0.0.1:8080 python scripts/acceptance_smoke.py
~~~

脚本不会打印 JWT。持久数据库环境应使用其生成的随机运行前缀，避免与旧验收记录冲突。

### 13.4 发布包检查

~~~bash
unzip -l agriloop-release-linux-x86_64.zip
sha256sum -c SHA256SUMS.txt
~~~

发布包允许的内容是 api JAR、Vite dist、db 迁移/种子、config、bin、manifest 和 README；禁止 Java/前端/微信源码、node_modules、Gradle 缓存、数据库 dump、日志、备份、.env 和模型权重。源码包同样排除 .git、node_modules、.gradle、build、dist、data、logs、backups、artifacts、.venv、__pycache__、.env 和模型权重。

### 13.5 独立环境安装检查

在与其他业务数据隔离的主机或 Docker 环境中，只使用发布 ZIP、源码包中的 Compose 文件和随机生成的配置完成安装。不要复制其他环境的数据库、配置、日志、备份或模型。最低检查项目：

1. 原生依赖或 Docker 服务启动。
2. Flyway 五个版本成功，虚拟种子导入。
3. 三角色登录和 /auth/me 范围正确。
4. /actuator/health 返回 UP。
5. 模拟遥测、SSE 和虚拟灌溉 ACK/效果可查询。
6. start、stop、restart、status、healthcheck 有效。
7. Nginx 四个路径可访问，AI 未启动时显示规则模式。

## 十四、日志、监控、备份和升级

API 标准输出、错误输出、Nginx 日志和 Supervisor 日志统一在 /srv/agriloop/shared/logs；数据库备份由 bin/backup.sh 和 /etc/cron.d/agriloop-backup 产生在 shared/backups。日志轮转不改变业务数据，备份文件必须受限存储。

升级采用 releases/<version> 和 current 符号链接。流程是备份、校验新 ZIP、在 releases 外解压、执行 install.sh、确认 current、重启并重新执行黑盒验收。不要删除旧版本，直到新版本健康和回滚窗口结束。恢复数据库先导入新建临时库核验，不直接覆盖生产库。

## 十五、扩展规范

1. 新指标先在 docs/api/schemas 和 OpenAPI 中登记编码、单位、范围、质量和来源，再修改 AgriEngine、SimulationEngine、前端标签和测试。
2. 新作物差异通过版本化 Crop Pack YAML 注入，遵循系统默认 -> Crop Pack -> 阶段 -> 农场 -> 地块解析顺序，不复制作物专用服务。
3. 新命令必须定义风险、权限、审批/确认、幂等键、ACK、超时、效果和审计字段；不能从 Agent 直达 MQTT。
4. 新持久化记录优先使用现有 entity_record 合同；需要结构化查询时先添加迁移和索引，不在业务代码中拼接不受控 SQL。
5. 新 Agent 工具必须加入 AgentToolRegistry，提供 JSON Schema、角色和导航映射，并增加越权、无效参数、重复确认和降级测试。
6. 新策略或模型只能通过离线回放和人工批准发布，不能在生产静默修改阈值。
7. 每次变更同步更新接口合同、部署/开发文档和自动化测试；删除字段时保留兼容期说明。
