# AgriLoop 项目现有不足与未来规划

> 文档用途：总结农智闭环（AgriLoop）整个项目的实现边界、主要不足和后续演进方向，重点覆盖数据、智能、可视化、仿真基础设施和 Agent，可用于项目评审、论文“局限性与展望”章节。
>
> 更新时间：2026-09-01

## 1. 总体结论

当前项目已围绕“模拟数据传输 → 规则/智能体决策 → 可视化呈现与操作”形成可运行的软件闭环。数据主线能够生成、校验、去重、评分并保存模拟遥测；业务层能够完成告警、诊断、预测、灌溉试算、农务和资源查询；前端提供三角色工作台、风险曲线、作物手册、Agent 对话和虚拟浇水操作；Agent 还能通过动作预览、安全门、人工确认、虚拟执行、ACK、效果评价和审计回放串起决策链路。

但当前实现的准确定位是：

> **面向本地仿真验收的模块化单体 + 规则优先的农业决策链 + 角色化 Agent 编排。**

项目仍处于软件仿真和受控演示阶段：它还不是多个独立 Agent 的自治协同系统，也不是已完成真实传感器、真实水泵/阀门和现场网关联调的生产控制系统。论文和答辩材料应明确区分“本地仿真验证”“后端增强切片”和“未来生产化能力”。

## 项目整体架构与当前交付边界

| 主线 | 当前实现 | 当前边界 |
| --- | --- | --- |
| 数据主线 | `SimulationEngine`、遥测质量、告警、PostgreSQL/H2/内存降级、SSE | 以模拟数据为主；真实设备和现场网关不计入本期完成 |
| 智能主线 | Crop Pack、规则/诊断/预测/就绪度、RAG/LLM 适配、Agent Tool 和安全门 | LLM 可选且默认可降级，模型不能绕过确定性规则 |
| 可视化主线 | 三角色工作台、地块总览、趋势曲线、风险预测、作物手册、农务、灌溉和审计 | 前端已覆盖主要演示链，复杂生产运营和跨租户协同仍需加强 |
| 仿真与基础设施 | 模块化单体、进程内模拟器、可选 MQTT/Redis Streams、Compose/Supervisor | 本地和受控环境优先，尚未证明高并发、多实例和长期运行 |
| 治理与证据 | JWT/RBAC、作用域、来源标签、版本、幂等、审计、ACK、效果评价 | 已具备可审计框架，但模型质量、真实效果和安全专项证据仍需积累 |

本期 P0 的验收重点是数据链路、规则告警、诊断处方、虚拟灌溉、三角色权限、Agent 降级和最小决策回放；预测校准、资源协同、经营价值、真实硬件和专业 Agent 协同属于后续增强方向。

## Agent 架构基线

### 2.1 统一编排与角色分流

Agent 入口由后端 `AgriEngine.agentChat` 统一处理。Agent 根据 JWT、角色、农场和地块作用域返回不同的能力画像：

| 角色 | 当前主要职责 | 当前权限边界 |
| --- | --- | --- |
| `SYSTEM_ADMIN` 系统管理员 Agent | 平台状态、跨农场风险、规则/策略版本、数据链路、决策审计 | 平台级只读，不直接修改农场业务 |
| `FARM_ADMIN` 农场管理员 Agent | 全场地块、告警诊断、农务派单、设备绑定、灌溉计划 | 可发起农场管理操作，但必须预览、复核和确认 |
| `FARMER` 农户 Agent | 本人负责地块、风险解释、今日待办、巡田记录、灌溉建议 | 只能操作授权地块，灌溉等写入动作必须本人确认 |

角色差异主要体现在作用域、可见事实、回答重点和可用工具，而不是三个独立的后端 Agent 服务。

### 2.2 当前业务意图与工具

统一编排器通过确定性意图路由支持以下主要能力：

- 地块状态：`PLOT_STATUS`
- 风险预测：`RISK_FORECAST`
- 根因诊断：`DIAGNOSIS`
- 灌溉建议：`IRRIGATION_RECOMMENDATION`
- 今日农务：`TODAY_WORK`
- 水资源状态：`WATER_RESOURCE_STATUS`
- 农场/平台概览：`FARM_OVERVIEW`、`PLATFORM_OVERVIEW`
- 平台和规则状态：`PLATFORM_STATUS`、`RULE_STRATEGY_STATUS`
- 图片分析：`IMAGE_ANALYSIS`
- 受控动作：`AGENT_ACTION`

写入型动作必须经过白名单和角色校验。当前工具包括地块创建/修改、设备绑定、告警核查、告警关闭、任务创建与派发、农户任务状态变更、巡田记录、补证任务和虚拟灌溉。

### 2.3 当前安全和降级机制

- 规则和确定性工具优先，模型只负责解释、组合和生成受控建议。
- 写入动作采用“计划 → 预览 → 重新授权 → 安全门 → 人工确认 → 执行”的流程。
- 动作带有风险等级、幂等键、十分钟 TTL 和显式状态，支持 `FAILED`、`PARTIAL`、`TIMEOUT`、`CANCELED` 等结果。
- LLM/RAG 不可用时降级为 `rules-only` 或 `mock`，前端显示降级状态。
- Agent 不直接生成任意 SQL、MQTT Topic 或 HTTP 控制命令。
- 运行、动作、消息、会话、工具输入输出和版本信息写入审计记录，并通过 SSE 刷新前端。

## 项目现有不足与局限

### 数据主线：真实度、连续性和覆盖面仍有限

当前数据链路已经覆盖模拟器、质量评分、告警、落库和 SSE 推送，但核心遥测主要由进程内 `SimulationEngine` 产生。不同设备型号、网络抖动、时钟漂移、批量上报、离线补传和真实现场噪声尚未被充分覆盖，人工观察与遥测的冲突样本也有限。

**影响：** 可以验证数据接入、质量门控和事件闭环，不能据此证明系统在真实田间网络、设备故障和跨季节数据下的稳定性。当前 `SIMULATED` 数据也不能替代 `OBSERVED/SIMULATION` 的现场证据。

### 作物与领域模型：可配置性已有，但农业有效性仍需验证

Crop Pack 已将作物档案、生育阶段、指标、规则、知识和情景集中配置，平台也具备多作物扩展结构。但 P0 仅要求少量完整 Crop Pack，其他作物包的规则阈值、知识覆盖、任务模板和回归证据仍需要农业专家校验；不同地区、设施和品种之间的参数继承也还不等同于经过田间验证。

**影响：** 系统具备“可扩展”的软件结构，但尚不能宣称所有作物和地区都具有同等决策准确性。

### 后端与接口：模块化单体便于交付，但边界仍需收敛

项目采用 Spring Boot 模块化单体，便于 15 天周期内完成跨模块联调；然而数据访问、业务规则、Agent、设备命令、审计和控制器仍在较大范围内共享实现。API 已有版本和 OpenAPI 描述，但跨模块错误码、幂等合同、分页、异步任务和长耗时操作的统一程度还需要提升。

**影响：** 当前适合单体部署和演示，后续扩展外部模型、更多设备、多个农场和高频事件时，接口变更和回归成本会增加。

### 前端与交互：功能覆盖较广，但生产运营体验仍需打磨

三角色工作台、地块总览、曲线、风险预测、作物手册、农务和 Agent 已形成主要演示链，但多个页面入口和较大的前端脚本分别维护角色状态、路由、轮询、SSE、演示数据和接口降级。复杂表格、长时间运行任务、移动端输入、无障碍、错误恢复和跨页面上下文一致性仍需要持续优化。

**影响：** 当前能够展示“看见—理解—行动”的核心路径，但距离生产人员每天高频使用的稳定工作台还有差距。

### 仿真与基础设施：本地可运行优先，规模化证据不足

项目支持 standalone、Compose 和 Supervisor 等运行方式，但模拟器可以在 API 进程内运行，SSE 订阅也主要是单实例内存状态；数据库、Redis、MQTT 不可用时存在降级路径。多实例事件广播、任务排队、消息重放、备份恢复、灰度升级和跨节点一致性尚未充分验证。

**影响：** 一键启动和故障降级有利于本地验收，但不能直接推导出生产环境的吞吐、可用性和灾备能力。

### 数据治理与隐私：演示边界清晰，生产治理仍需补齐

当前已使用虚拟账号、虚拟地块和来源标签，并限制 Agent 的数据作用域；但生产环境仍需完善租户隔离、数据保留周期、附件对象存储、加密、密钥轮换、审计不可篡改、个人信息最小化和导出脱敏策略。

**影响：** 演示数据可控，不等同于农业企业、合作社或跨组织场景下的合规治理能力。

### Agent：角色化单体，不是多 Agent 协同

当前的“感知 Agent、诊断 Agent、处方 Agent”等更多是能力和流程概念，代码中主要表现为同一 `AgriEngine` 内的意图分支和工具调用。它们没有独立的消息协议、状态机、生命周期和协作调度机制。

**影响：** 专业能力之间的职责边界和并行协作能力还不够清晰，难以直接验证多 Agent 协商、冲突解决和任务转交效果。

### Agent：核心类体量较大，维护和演进成本较高

Agent、业务查询、预测、动作治理、模型适配、持久化和控制流程集中在 [`AgriApplication.java`](../apps/api-service/src/main/java/com/agriloop/AgriApplication.java) 的模块化单体中，`AgriEngine` 负责的逻辑范围较广。

**影响：** 现阶段便于本地一键运行和联调，但新增作物、工具、模型适配器或权限规则时，回归范围较大，长期维护容易出现领域耦合。

### Agent：意图识别对固定表达依赖较强

确定性快速路径大量使用关键词、正则和固定分支。它对常见中文问题稳定，但对多意图请求、模糊指代、复杂上下文、同义表达和跨轮任务的泛化能力有限。

**影响：** 可能出现意图误判、参数缺失或需要用户重复改写问题；当前对话历史主要用于有限的追问承接，不是完整的长期记忆系统。

### Agent：模型和 RAG 的质量证据仍不充分

默认配置为 `AI_MODE=openai-compatible`，模型不可用时明确降级为 `rules-only`；`maxkb` 和 `mock` 仍可按部署需要选择。当前 Crop Pack 知识目录已经可用，但还缺少系统性的召回评测、引用正确率、知识新鲜度和冲突证据指标。

**影响：** 能够保证模型不可用时核心流程继续运行，但尚不能据此证明 LLM 的农业知识准确率、复杂问答能力或跨作物泛化能力。

### 智能决策：预测结果主要服务于仿真验证

当前风险预测依赖模拟遥测和确定性趋势逻辑，已经具备预测区间、时间窗、策略版本和就绪度字段，但仍缺少长期真实数据、外部天气、跨季节样本和充分的回测校准。

**影响：** 预测可以用于演示“趋势—风险—处置”的闭环，不应直接表述为经过真实农业生产验证的预测模型。

### 执行与设备：仍停留在虚拟设备边界

虚拟命令、ACK、效果评价和模拟遥测回写已经形成闭环；但真实水泵、阀门、GPIO、现场网关和物理急停不属于当前交付范围。

**影响：** 当前系统能够验证权限、幂等、安全门和非成功路径，不能证明物理控制的时延、故障安全和现场可靠性。

### 学习与经营：尚未形成生产级闭环

项目已经具备案例、策略候选、离线验证、决策账本和价值查询等后端切片，但策略更新必须经过离线回放和人工批准，不支持生产态静默自改。缺少完整产量、价格、成本和反事实数据时，也不能宣称真实收益或避免损失。

**影响：** 当前更适合展示“可审计的反馈与候选策略”，还不能证明在线自学习或真实经济效益。

### 平台工程：持久化、并发和可观测性仍需生产化

standalone 模式存在内存降级，模拟器和 SSE 主要在 API 进程内运行；多实例场景下仍需要共享事件、统一追踪和一致性方案。现有审计记录较完整，但模型耗时、Token/成本、工具失败率、队列堆积和端到端 SLO 还需要统一监控。

**影响：** 当前架构适合 15 天范围的本地和受控演示，尚未证明大规模、多租户和长期运行能力。

### 治理与验收：安全测试和状态证据仍需持续收口

现有权限、白名单、幂等和安全门已经覆盖主要路径，但生产化仍需要补充提示词注入、数据越权、敏感信息泄露、频率限制、密钥轮换和不可抵赖审计等专项验证。

同时，项目文档中部分 P1/P2 后端切片已标记为完成，而 `PROJECT_STATUS.md` 中仍存在“本地验收、待用户验收”的条目。代码落盘不等于完整功能、前端交互、长期运行和生产证据全部完成，状态和证据需要继续保持同步。

## 未来规划

### P1：近期完善方向

| 方向 | 规划内容 | 预期证据 |
| --- | --- | --- |
| 数据主线增强 | 补充真实格式样本、网络抖动、离线补传、时钟漂移、批量上报和人工观察冲突回放；完善事件去重、质量评分和数据新鲜度指标 | MQTT → Streams → 数据库 → SSE 集成测试，异常样本回放，端到端延迟和丢失率指标 |

| 后端接口收敛 | 统一错误码、分页、幂等键、异步任务、长耗时查询和 OpenAPI 合同，进一步明确模块之间的读写边界 | OpenAPI 解析、接口契约测试、重复请求和版本冲突测试 |
| 前端工作台治理 | 抽取共享状态、权限、路由、实时刷新和降级组件，减少角色入口之间的重复逻辑；完善移动端、无障碍、错误恢复和长任务反馈 | 三角色浏览器回归、窄屏检查、SSE 断线恢复、无控制台错误 |
| 仿真与运维 | 增加可配置场景编排、消息重放、备份恢复、健康检查、运行指标、日志关联和多实例 SSE 方案 | 固定 `scenarioId` 回放、重启恢复、故障注入、P95 延迟和可用性记录 |
| 安全与隐私 | 完善租户隔离、附件存储、加密、密钥轮换、限流、提示词注入防护、导出脱敏和审计保留策略 | RBAC/越权、注入、敏感数据、密钥和审计专项测试 |
| Agent 内部模块化 | 将统一编排器拆为 Gateway、Context Builder、Intent Router、Evidence Service、Model Adapter、Action Governance、Audit Service；仍保持模块化单体 | 模块边界、接口测试和回放结果不变 |
| 结构化意图与工具调用 | 以 JSON Schema 约束意图和工具参数，补充缺参追问、多意图排序、上下文摘要和 `UNAVAILABLE` 分支 | 固定问题结构化输出成功率、工具参数校验和越权测试 |
| RAG 知识治理 | 按“地块 → 农场/地区 → 生育期 → 作物 → 通用知识”分层检索，保存引用、版本、有效期和冲突证据 | 检索准确率、引用完整率、知识版本回放 |
| 预测可信度 | 完善 forecast snapshot、Time-to-Risk、预测区间、算法版本、数据覆盖率和失准监测 | 固定场景回测、预测可追溯率和失准告警 |
| 决策护照与效果评价 | 将观测、推导、模拟、估算、人工输入、处方、命令、ACK 和效果统一关联 | `traceId` 链路完整、非成功执行不误标成功 |
| 资源和协同约束 | 将可用水量、设备能力、人员工时、时间窗和优先级纳入 Agent 建议和冲突解释 | 受限水源和多地块资源分配回归，容量超限为 0 |
| 安全与可观测性 | 增加提示词注入、越权、敏感数据、幂等并发、限流和审计完整性测试，统一记录延迟、失败率和降级原因 | 安全回归、SLO 指标和审计字段完整率 |

### P2：中长期演进方向

P2 以“生产化、规模化和行业化”为目标，必须建立在 P0/P1 的回放、测试、数据治理和人工验收证据之上。任何新能力都应继续复用统一事件、命令、Crop Pack、Agent Tool、安全门和审计体系，避免出现无法追踪的平行闭环。

#### 受控的专业 Agent 协同

在统一编排器下增加感知、诊断、预测、处方、资源调度和审计等专业 Agent。专业 Agent 只通过版本化消息和受控工具交换结果，共享同一证据链、决策护照、安全门和审计账本，不建立平行控制闭环。

#### 真实设备适配

在虚拟执行充分验证后，增加 `REAL/HARDWARE` 数据源、设备网关、签名命令、设备证书、急停、人工接管、断网恢复和物理安全联锁。真实硬件联调完成前，不把该能力写成当前项目成果。

#### 规模化和多租户运行

将进程内模拟器、SSE 和本地降级存储逐步替换为可水平扩展的任务执行、事件推送、共享存储和租户隔离方案，并保持现有事件、命令、Agent Tool 和审计合同不变。

#### 受控学习与经营价值

只使用已完成效果评价且质量合格的案例生成 `strategy_candidate`，经过离线回放、自动回归和人工批准后发布。进一步接入产量、价格、能耗、工时和成本数据，区分观察值、用户输入、推导值、模拟值和估算值，再进行经营价值分析。

#### 多模态和外部知识扩展

在图片证据、外部天气和语音入口具备稳定评测集、隐私处理和失败降级后，再扩展到病害识别、天气联合预测和语音交互；这些能力不能替代确定性规则和安全门。

## 分阶段验收边界

### P0：当前可交付范围

- 模拟数据生成、质量评分、告警、落库和 SSE/REST 查询闭环。
- 三角色工作台、地块总览、历史/预测曲线、作物培养手册和农务入口。
- 三角色统一 Agent 入口和角色作用域。
- 确定性状态、诊断、预测、就绪度和灌溉工具。
- Crop Pack 知识、规则优先和 `rules-only/mock` 降级。
- 动作白名单、预览、确认、幂等、TTL、虚拟执行、ACK 和效果评价。
- Agent 运行、动作、消息、会话和事件审计。
- `normal`、`drought`、`heavy-rain`、`sensor-drift`、`device-offline`、`evidence-conflict` 等仿真场景。

### P1：已有后端切片但需要持续验收和生产化

- 数据回放、接口合同、前端实时刷新、运行健康和备份恢复的持续验证。
- 短期预测、Time-to-Risk、What-if 双轨。
- 受限水源资源计划、计划与实际、价值账本。
- 相似案例、决策护照和策略候选。
- 前后端一致性、持续运行、模型质量和长期回放证据。

### P2：后续演进，不计入当前完成声明

- 专业 Agent 的独立协同调度。
- 真实泵阀、现场网关和物理安全联锁。
- 生产级多租户、高并发和跨实例事件总线。
- 经过因果验证的在线学习、收益归因、视觉病害和语音交互。

## 论文可直接使用的总结

本项目当前围绕“模拟数据传输—确定性农业决策—可视化呈现与受控操作”构建了可复现的软件闭环，并以统一 Agent 编排器、Crop Pack、规则引擎、虚拟执行器和审计链路串联三条主线。该方案优先保证数据来源、规则判断和控制动作的可追溯性，适合 15 天周期内的本地仿真与受控演示。项目局限主要体现在：真实传感器和设备数据不足，Crop Pack 的农业有效性仍需专家与田间验证，后端和前端模块边界仍需收敛，预测与 RAG 缺少长期质量证据，Agent 尚未形成专业协同，平台的多实例、隐私治理和生产运维能力也未充分证明。后续将按照 P1/P2 分阶段推进数据质量、作物模型、接口和工作台治理、Agent 结构化调用、预测校准、RAG 评测、资源协同、受控学习、真实设备适配和规模化部署，在不破坏规则优先、安全门和审计边界的前提下，形成可扩展、可验证的农业智能决策系统。
